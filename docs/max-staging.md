# Проверка сценария в настоящем MAX

Этот порядок рассчитан на отдельный тестовый дом и тестового бота. Локальный профиль `demo` для проверки в MAX не подходит: он подменяет вход и не отправляет уведомления.

## Что потребуется

1. Создать тестового бота на [платформе MAX для партнёров](https://business.max.ru/) и получить его токен. Токен хранить только в локальном `.env` стенда или в хранилище секретов, не в Git и не в переписке.
2. Подготовить публичный домен с HTTPS и доверенным сертификатом. Прокси должен передавать все пути на backend `127.0.0.1:8080`: приложение, `/v1/**`, `/webhooks/max` и `/actuator/health`. [MAX требует HTTPS для webhook](https://dev.max.ru/docs-api/methods/POST/subscriptions) и [для URL мини-приложения](https://dev.max.ru/docs/webapps/introduction).
3. В `.env` стенда задать `MAX_BOT_TOKEN`, `MAX_WEBHOOK_SECRET`, `MAX_PUBLIC_URL=https://...` и `HOST_BIND_IP=127.0.0.1`. Секрет webhook должен состоять из 5–256 букв, цифр, `_` или `-`. `MAX_PUBLIC_URL` — базовый адрес без завершающего `/`.

## Запуск и подключение

```sh
docker compose up --build -d
python3 scripts/max_staging.py check
python3 scripts/max_staging.py subscribe
```

Команда `check` проверяет HTTPS-адрес backend и мини-приложения, токен через `GET /me` и доступ к подпискам. Она не выводит секреты. `subscribe` явно регистрирует `https://<домен>/webhooks/max` для событий `message_created` и `bot_started`; повторный запуск не создаёт подписку с тем же URL. Если проверка не прошла, подписка не создаётся.

В настройках бота MAX указать URL кнопки мини-приложения: `https://<домен>/miniapp/index.html`. Это действие выполняется на платформе MAX. В самом мини-приложении пользователь с ролью диспетчера увидит переход в свой кабинет; при переходе сохраняются параметры запуска MAX.

## Тестовый дом и роли

После запуска Flyway создать тестовый дом и приглашение в БД стенда:

```sh
docker compose run --rm staging-seed --db /app/data/pulse-doma.db house --address "Тестовый дом"
docker compose run --rm staging-seed --db /app/data/pulse-doma.db invite --house-id <house_id>
```

Приглашение действует 7 дней и допускает 10 активаций. Токен из вывода передать двум тестовым участникам приватно. Они открывают мини-приложение по [диплинку MAX](https://dev.max.ru/docs/webapps/introduction): `https://max.ru/<имя_бота>?startapp=<токен>`.

После первого входа будущего диспетчера найти его MAX ID и выдать роль в тестовом доме:

```sh
docker compose run --rm staging-seed --db /app/data/pulse-doma.db users
docker compose run --rm staging-seed --db /app/data/pulse-doma.db dispatcher --house-id <house_id> --max-user-id <max_user_id>
```

После повторного открытия мини-приложения диспетчер должен увидеть кнопку «Открыть кабинет диспетчера».

## Сценарий приёмки

1. Житель открывает мини-приложение из MAX, выбирает тестовый дом, заполняет место, время и описание, прикрепляет фото и создаёт новую заявку.
2. Диспетчер открывает кабинет через мини-приложение, принимает заявку и проводит её через `ASSIGNED` и `IN_PROGRESS` до выполнения.
3. Житель получает сообщение от бота MAX и видит в «Моих заявках» запрос подтверждения. Первый раз отвечает «Проблема осталась»; диспетчер видит повторно открытую заявку.
4. Диспетчер повторяет работу. Житель подтверждает решение; заявка получает `CLOSED_CONFIRMED`.
5. Проверить в БД `status_events`, `issue_verification_responses` и `notification_outbox`: статусная история полная, ответ записан, уведомление имеет `sent_at`.

Перед выключением стенда удалить тестовую подписку командой `python3 scripts/max_staging.py unsubscribe`, которая вызывает [DELETE `/subscriptions`](https://dev.max.ru/docs-api/methods/DELETE/subscriptions). Реальный клиент MAX и доставка сообщения пока не проверены; этот документ задаёт порядок будущей проверки.
