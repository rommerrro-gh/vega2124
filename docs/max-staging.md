# Проверка сценария в настоящем MAX

Этот порядок рассчитан на отдельный тестовый дом и тестового бота. Локальный профиль `demo` для проверки в MAX не подходит: он подменяет вход и не отправляет уведомления.

## Что потребуется

1. Использовать выданного организаторами тестового бота MAX и его токен. Токен хранить только в локальном `.env` стенда или в хранилище секретов, не в Git и не в переписке.
2. Подготовить публичный домен с HTTPS и доверенным сертификатом. Прокси должен передавать все пути на backend `127.0.0.1:8080`: приложение, `/v1/**`, `/webhooks/max` и `/actuator/health`. [MAX требует HTTPS для webhook](https://dev.max.ru/docs-api/methods/POST/subscriptions) и [для URL мини-приложения](https://dev.max.ru/docs/webapps/introduction).
3. В `.env` стенда задать `MAX_BOT_TOKEN`, `MAX_BOT_USERNAME`, `MAX_WEBHOOK_SECRET`, `MAX_PUBLIC_URL=https://...`, `HOST_BIND_IP=127.0.0.1` и `SPRING_PROFILES_ACTIVE=` (профиль `demo` предназначен только для локального просмотра). Секрет webhook должен состоять из 5–256 букв, цифр, `_` или `-`. `MAX_PUBLIC_URL` — базовый адрес без завершающего `/`.
4. Для личной демонстрации экспертов задайте `GUIDED_DEMO_CODE_SHA256`: SHA-256 от отдельного случайного кода. Сам код передайте судьям отдельно. Перезапустите backend после изменения `.env`. Пустое значение отключает вход по коду.

## Запуск и подключение

```sh
docker compose up --build -d
python3 scripts/max_staging.py check
python3 scripts/max_staging.py subscribe
```

Команда `check` проверяет HTTPS-адрес backend и мини-приложения, токен через `GET /me` и доступ к подпискам. Она не выводит секреты. Скрипт добавляет [корневой сертификат Минцифры](../infra/certs/russian_trusted_root_ca.pem) к системным доверенным сертификатам Python; Java-образ содержит тот же сертификат для исходящих запросов к MAX API. Сертификат получен с [официального адреса](https://gu-st.ru/content/Other/doc/russian_trusted_root_ca.cer), его SHA-256 fingerprint: `D2:6D:2D:02:31:B7:C3:9F:92:CC:73:85:12:BA:54:10:35:19:E4:40:5D:68:B5:BD:70:3E:97:88:CA:8E:CF:31`. Проверка TLS не отключается. `subscribe` явно регистрирует `https://<домен>/webhooks/max` для событий `message_created` и `bot_started`; повторный запуск не создаёт подписку с тем же URL. Если проверка не прошла, подписка не создаётся.

Для выданного организаторами бота MAX отправьте URL мини-приложения `https://www.pulsedoma.ru/miniapp/index.html` через [форму подключения](https://sbor-ssylok-dlya-mini-prilojeniy.testograf.ru/). Форма запрашивает фамилию и имя капитана команды, email капитана, указанный при регистрации, название команды и URL мини-приложения. Токен бота туда не передаётся. После отправки форма сообщает, что ссылка получена и подключение ожидается в течение трёх часов; по вопросам указан `support@hackathon-max.vk.company`. 29 сентября путь формы был проверен на явно тестовых данных; позднее команда сообщила, что отправила настоящую заявку. Подключение организаторами пока не подтверждено. Если у команды есть доступ к настройкам собственного бота на платформе MAX, URL можно установить непосредственно там.

В самом мини-приложении пользователь с ролью диспетчера увидит переход в свой кабинет; при переходе сохраняются параметры запуска MAX.

После события `bot_started` бот отправляет описание паспорта дома, контактов, опросов и обращений с кнопкой открытия мини-приложения. Команды `/start`, `/help` и «помощь» повторяют сообщение. Для проверки внутри MAX судья вводит код на первой странице; его тестовый дом и роли жителя и диспетчера изолированы от других судей. Подробный [маршрут судьи](judge-demo.md) не требует выдавать ему административные роли.

## Тестовый дом и роли

Будущий системный администратор сначала открывает mini app из MAX. Его профиль создаётся без доступа. Затем однократно назначьте роль по его MAX ID:

```sh
docker compose run --rm staging-seed --db /app/data/pulse-doma.db users
docker compose run --rm staging-seed --db /app/data/pulse-doma.db system-admin --max-user-id <max_user_id>
```

После повторного открытия mini app он переходит в кабинет `/system/index.html`, создаёт тестовую УК и дом, закрепляет дом за УК и приглашает администратора УК. Тот принимает ссылку в MAX, открывает `/uk/index.html` и приглашает диспетчера и администратора дома. Администратор дома приглашает двух тестовых жильцов. Каждая ссылка открывается через [диплинк MAX](https://dev.max.ru/docs/webapps/introduction) и требует подтверждения роли и дома перед активацией. Готовая ссылка формируется в кабинете при заданном `MAX_BOT_USERNAME`.

Подробные правила, сроки ссылок и отзыв доступа описаны в [активации пользователей](access-activation.md). Старые команды `house`, `invite`, `dispatcher` и `admin` в скрипте остаются для совместимости с прежним стендом; новый сценарий ролей проходит через интерфейсы.

### Проверка двумя аккаунтами

Для основной цепочки достаточно двух разных аккаунтов MAX: A — системный администратор, администратор УК, администратор дома и диспетчер; B — житель. Приложение допускает несколько ролей у одного пользователя. Эти назначения создаются отдельными приглашениями, даже если A сам их выпустил: код принятия приглашений не запрещает принять собственное. Если этот путь даст ошибку в реальном клиенте, зафиксируйте её и используйте отдельного участника для административных ролей.

1. Дождитесь, пока организаторы подключат ссылку к боту `t802_hakaton_max_bot`. Оба участника должны открыть бот в MAX и запустить мини-приложение через его кнопку. Открытие URL в обычном браузере не передаёт подписанные данные MAX.
2. A впервые открывает мини-приложение. Появляется профиль без роли. На сервере в `/home/deploy/pulsedoma-max` выполните `docker compose run --rm staging-seed --db /app/data/pulse-doma.db users`, найдите MAX ID A, затем `docker compose run --rm staging-seed --db /app/data/pulse-doma.db system-admin --max-user-id <MAX_ID_A>`. Назначение первого системного администратора одноразовое.
3. A повторно открывает мини-приложение, входит в «Управление системой», создаёт тестовую УК и дом, закрепляет дом за УК. Выпускает приглашение `UK_ADMIN` на этот дом и принимает его под A через ссылку `https://max.ru/t802_hakaton_max_bot?startapp=<token>`.
4. В «Кабинете УК» A выпускает и принимает под собой два отдельных приглашения на тот же дом: `DISPATCHER` и `HOUSE_ADMIN`. В кабинете администратора дома A выпускает приглашение `RESIDENT`, которое принимает B. Административные приглашения одноразовые и действуют 72 часа; ссылку жителя можно сделать на несколько активаций.
5. A проверяет, что в кабинете диспетчера виден выбранный дом; B проверяет, что в кабинете жителя доступно создание обращения. Затем выполняется сценарий ниже.

## Сценарий приёмки

1. Житель открывает мини-приложение из MAX, выбирает тестовый дом, заполняет место, время и описание, прикрепляет фото и создаёт новую заявку.
2. Диспетчер открывает кабинет через мини-приложение, принимает заявку и проводит её через `ASSIGNED` и `IN_PROGRESS` до выполнения.
3. Житель получает сообщение от бота MAX и видит в «Моих заявках» запрос подтверждения. Первый раз отвечает «Проблема осталась»; диспетчер видит повторно открытую заявку.
4. Диспетчер повторяет работу. Житель подтверждает решение; заявка получает `CLOSED_CONFIRMED`.
5. Проверить в БД `status_events`, `issue_verification_responses` и `notification_outbox`: статусная история полная, ответ записан, уведомление имеет `sent_at`.

Перед выключением стенда удалить тестовую подписку командой `python3 scripts/max_staging.py unsubscribe`, которая вызывает [DELETE `/subscriptions`](https://dev.max.ru/docs-api/methods/DELETE/subscriptions). Реальный клиент MAX и доставка сообщения пока не проверены; этот документ задаёт порядок будущей проверки.
