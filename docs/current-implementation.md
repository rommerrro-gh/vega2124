# Пульс дома: текущее состояние реализации

Актуально для ветки `feature/pulse-doma-skeleton` на 24 сентября 2026 года. Этот файл ведём вместе с кодом: при изменении поведения, конфигурации или результатов проверки обновляем соответствующий раздел в том же pull request.

Продуктовые требования остаются в [продуктовой концепции](pulse-doma-product.pdf), технические требования — в [ТЗ](pulse-doma-technical-specification.pdf). [OpenAPI](../infra/openapi.yaml) задаёт контракт HTTP-маршрутов, [README](../README.md) содержит команды локального запуска. Ни наличие маршрута, ни наличие таблицы сами по себе не означают, что пользовательский сценарий реализован.

## Что можно запустить сейчас

Проект — Maven reactor из 10 модулей на Java 21 и Spring Boot 3.1.0. Исполняемый Java-модуль один: `app-bootstrap`. Он собирает Spring Boot JAR, конфигурацию запуска и зависимости остальных модулей.

| Модуль | Назначение | Отдельный процесс |
| --- | --- | --- |
| `app-bootstrap` | Точка входа, безопасность, DataSource, Redis-очередь, обработка ошибок | Да |
| `api` | Контроллеры и входные DTO | Нет |
| `domain-identity`, `domain-issues`, `domain-duplicates`, `domain-house` | Модели и начальные доменные правила | Нет |
| `integration-max`, `integration-external` | Клиенты и контракты внешних интеграций | Нет |
| `common` | Общие контракты, ошибки, correlation ID | Нет |
| `infra` | Миграция SQLite, OpenAPI, демонстрационные данные | Нет |

`compose.yaml` поднимает четыре контейнера: `backend`, Redis, MinIO и демонстрационный `contract-adapter` на nginx. Снаружи открыты порт backend `8080` и порты MinIO `9000`/`9001`; Redis и adapter доступны контейнерам внутри сети Compose. SQLite хранится в volume `sqlite-data`, Redis и MinIO используют отдельные volumes. Единственный `application.yaml` для Java-процесса находится в `app-bootstrap/src/main/resources/`; значения порта, БД, Redis, MAX, MinIO и adapter можно переопределить переменными окружения. Локальный `.env` не коммитится.

## Реализовано

- **Хранение данных.** Миграция `V1__init.sql` создаёт основные таблицы, `V2__fts5.sql` добавляет `issues_fts`, поисковые поля заявок и `correlation_id`. SQLite настроена на WAL, `busy_timeout=5000`, `foreign_keys=ON` и один connection в Hikari. Демонстрационные записи из `infra/seed/demo.sql` применяются вручную.
- **Модели и типы.** Для статусов пользователя, членства, подтверждения, заявки, внешнего тикета и приоритета применяются Java `enum`; JPA хранит их как строковые значения через `EnumType.STRING`. Входные DTO контроллеров используют Bean Validation. `.gitignore` исключает `.env`, локальные файлы БД, результаты сборки и файлы IntelliJ IDEA.
- **HTTP-контракт.** Всем операциям из `infra/openapi.yaml` соответствуют маршруты контроллеров в `api`. Реализованы `POST /webhooks/max` и контроллер `POST /v1/reports` с ответом `201`; остальные операции отвечают `501` в изолированных тестах. В запускаемом приложении доступ к `/v1/**` пока закрыт правилом безопасности до появления JWT.
- **Webhook MAX.** Контроллер проверяет секрет и кладёт JSON в Redis list `max:webhook:updates`. Worker извлекает события через LPOP, обрабатывает `message_created`, использует Redis Set для дедупликации по `body.mid`, делает повторы с backoff и отправляет событие в dead-letter list после пяти ошибок. Для маршрутизации нужны записи `users.max_user_id` и `chat_bindings`.
- **Домен и интеграции.** `ReportService` нормализует текст, сохраняет обращение, выбирает до 10 кандидатов по дому, статусу и времени; score от 0,82 возвращает кандидатов, диапазон 0,65–0,82 помечается для проверки, а ниже 0,65 создаётся `DRAFT` с базовым SLA. Действия пишутся в аудит. `MaxApiClient` содержит клиент для MAX API; внешний adapter пока контрактная заглушка. Точный SLA и скоринг по зоне требуют продуктовых правил.
- **Проверки.** GitHub Actions выполняет `mvn -B clean verify`. Есть три теста контрактов контроллеров и тест запуска Spring-контекста. Они проверяют регистрацию маршрутов, часть валидации, webhook и старт приложения, но не бизнес-процесс целиком.

## Изменения относительно исходного ТЗ и первого каркаса

| Область | Текущее решение |
| --- | --- |
| Структура | Модули разделены на один запускаемый Java-сервис и девять библиотек/модулей ресурсов. Для библиотек отдельные `application.yaml` не нужны. |
| Webhook | HTTP-контроллер расположен в `api`, реализация Redis-очереди — в `app-bootstrap`; в ТЗ вход webhook описан в `integration-max`. |
| Контроллеры | Добавлены маршруты всей OpenAPI-спецификации, аннотации валидации и типизированные перечисления. `@Validated`-контроллеры оставлены не `final`, чтобы Spring мог создать CGLIB-прокси. Незавершённые операции возвращают `501`. |
| Версии | В сборке зафиксированы Flyway `9.16.3` и SQLite JDBC `3.43.0.0`; в ТЗ указаны Flyway `9.22.x` и SQLite `3.46`. Версии ТЗ и проекта нужно согласовать перед релизом. |
| Compose | Добавлены проверки готовности сервисов. Для локального MinIO используется community-образ Coollabs, закреплённый по digest: прежний образ не загружался. Выбор S3-хранилища для промышленной среды остаётся отдельным решением. |
| Конфигурация Flyway | Коммит тиммейта `408019a` добавил `spring.flyway.clean-on-validation-error: true` и `clean-disabled: false` с пометкой «для разработки». При ошибке валидации миграций это разрешает полную очистку БД; использовать такую конфигурацию с ценными данными нельзя. Перед общим или промышленным развёртыванием нужен безопасный профиль/значения по умолчанию. |

История этапа: создан Maven-каркас и схема БД; затем уточнены версии зависимостей и Dockerfile; добавлены типизированные поля, валидация и покрытие маршрутов; исправлен запуск `@Validated`-контроллеров; заменён недоступный образ MinIO; выполнена проверка Compose; добавлены параметры очистки Flyway для разработки. Детали отдельных правок можно смотреть в истории коммитов ветки.

## Что проверено на практике

24 сентября 2026 года `docker compose -p pulse-doma-check up --build -d` собрал backend и поднял все четыре контейнера до состояния `healthy`. Spring Boot запустился, Flyway применил миграцию V1, `/actuator/health` вернул `UP`, endpoint здоровья MinIO ответил `200`. Проверочный webhook с верным секретом вернул `200` и увеличил длину Redis-очереди с 0 до 1; неверный секрет вернул `401`, некорректное тело — `400`. После проверки контейнеры и сеть остановлены через `docker compose -p pulse-doma-check down`; volumes с данными сохранены. Проверка проводилась до добавления двух параметров Flyway в последнем коммите тиммейта.

Maven-сборка и тесты также прошли в [GitHub Actions](https://github.com/rommerrro-gh/vega2124/actions/runs/36029444359). Это подтверждает сборку каркаса и перечисленные smoke-проверки, но не запуск сценария с реальным ботом MAX, загрузку вложений или выполнение критериев приёмки ТЗ.

## Что ещё предстоит

1. Реализовать JWT-аутентификацию, роли и `house scope`, затем открыть необходимые `/v1/**` маршруты.
2. Завершить путь `MAX → report → issue → candidates → join/create → статус → уведомление → приёмка`: добавить выбор кандидата, создание привязки, переходы статуса и уведомления, а также надёжное восстановление элемента очереди после аварии между LPOP и обработкой.
3. Завершить бизнес-операции заявок, обращений, инцидентов, данных дома и интеграций; убрать `501` только после реализации и тестирования соответствующего сценария.
4. Подключить загрузку вложений в S3-совместимое хранилище, политики доступа и очистку данных.
5. Согласовать версии зависимостей и безопасные настройки Flyway, затем проверить критерии приёмки и нефункциональные требования из ТЗ на отдельном окружении.

При каждой следующей правке указывайте здесь фактическое состояние, подтверждённые проверки и оставшиеся ограничения. Для содержательных изменений синхронно обновляйте OpenAPI и README.
