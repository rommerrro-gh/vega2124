# Пульс дома: текущее состояние реализации

Актуально для ветки `feature/critical-path` на 28 сентября 2026 года. Этот файл ведём вместе с кодом: при изменении поведения, конфигурации или результатов проверки обновляем соответствующий раздел в том же pull request.

Продуктовые требования остаются в [продуктовой концепции](pulse-doma-product.pdf), технические требования — в [ТЗ](pulse-doma-technical-specification.pdf). [OpenAPI](../infra/openapi.yaml) задаёт контракт HTTP-маршрутов, [README](../README.md) содержит команды локального запуска. Ни наличие маршрута, ни наличие таблицы сами по себе не означают, что пользовательский сценарий реализован.

## Что можно запустить сейчас

Проект — Maven reactor из 10 модулей на Java 21 и Spring Boot 3.1.0. Исполняемый Java-модуль один: `app-bootstrap`. Он собирает Spring Boot JAR, конфигурацию запуска и зависимости остальных модулей.

| Модуль | Назначение | Отдельный процесс |
| --- | --- | --- |
| `app-bootstrap` | Точка входа, безопасность, DataSource, Redis-очередь, обработка ошибок | Да |
| `api` | Контроллеры и входные DTO | Нет |
| `domain-identity`, `domain-issues`, `domain-duplicates`, `domain-house` | Модели и начальные доменные правила | Нет |
| `integration-max`, `integration-external` | Клиенты и контракты внешних интеграций | Нет |
| `common` | Общие контракты, ошибки, correlation ID | Нет |
| `infra` | Миграция SQLite, OpenAPI, демонстрационные данные | Нет |

`compose.yaml` поднимает четыре контейнера: `backend`, Redis, MinIO и демонстрационный `contract-adapter` на nginx. Снаружи открыты порт backend `8080` и порты MinIO `9000`/`9001`; Redis и adapter доступны контейнерам внутри сети Compose. SQLite хранится в volume `sqlite-data`, Redis и MinIO используют отдельные volumes. Единственный `application.yaml` для Java-процесса находится в `app-bootstrap/src/main/resources/`; значения порта, БД, Redis, MAX, MinIO и adapter можно переопределить переменными окружения. Локальный `.env` не коммитится.

Интерфейсы жителя и диспетчера собираются из `frontend/` на React 19 и MAX UI 0.5.0. Готовые панели, кнопки и ячейки MAX UI дополнены цветами «Пульса дома»; собранные файлы лежат в `static/miniapp/` и обслуживаются тем же Spring Boot без изменений Java API. Команды сборки фронта приведены в [README](../README.md#mini-app).

## Реализовано

- **Хранение данных.** Миграция `V1__init.sql` создаёт основные таблицы, `V2__fts5.sql` добавляет `issues_fts`, поисковые поля заявок и `correlation_id`. SQLite настроена на WAL, `busy_timeout=5000`, `foreign_keys=ON` и один connection в Hikari. Демонстрационные записи из `infra/seed/demo.sql` применяются вручную.
- **Модели и типы.** Для статусов пользователя, членства, подтверждения, заявки, внешнего тикета и приоритета применяются Java `enum`; JPA хранит их как строковые значения через `EnumType.STRING`. Входные DTO контроллеров используют Bean Validation. `.gitignore` исключает `.env`, локальные файлы БД, результаты сборки и файлы IntelliJ IDEA.
- **HTTP-контракт.** Реализованы webhook, приём приглашения, список домов и заявок жителя, создание обращения, загрузка и чтение вложений, создание и присоединение к заявке, чтение карточки, очередь диспетчера, рабочие переходы статуса и подтверждение результата. Остальные операции отвечают `501`. Для `/v1/**` проверяется подпись `MAX WebApp.initData`; профиль `demo` даёт только локальный тестовый вход для жителя и диспетчера. Автор запроса определяется сервером, не полем `authorId` клиента.
- **Webhook MAX.** Контроллер проверяет секрет и кладёт JSON в Redis list `max:webhook:updates`. Worker извлекает события через LPOP, обрабатывает `message_created`, использует Redis Set для дедупликации по `body.mid`, делает повторы с backoff и отправляет событие в dead-letter list после пяти ошибок. Для маршрутизации нужны записи `users.max_user_id` и `chat_bindings`.
- **Домен и интеграции.** Форма собирает категорию, место, время, описание и до пяти файлов по 10 МБ. `ReportService` сохраняет обращение и ищет кандидатов того же дома, категории и нормализованного места. Черновик заявки создаётся только после явного выбора жителя; присоединение проверяет дом, активный статус и владельца обращения. Вложения хранятся в частном MinIO bucket, а в профиле `demo` — локально; чтение ограничено автором, участниками и диспетчером дома. Кабинет диспетчера находится в `static/dispatcher`, очередь ограничена ролью `DISPATCHER` и домом. После `RESOLVED` начинается `VERIFICATION_72H`: все участники должны подтвердить результат, отказ возвращает заявку в `REOPENED`, истечение срока закрывает её как `CLOSED_UNCONFIRMED`. Ответы, статусы и сроки хранятся в SQLite. Сообщения MAX ставятся в `notification_outbox` в той же транзакции, затем отдельное задание отправляет их с повторными попытками; профиль `demo` наружу не отправляет. Внешний adapter пока контрактная заглушка.
- **Проверки.** GitHub Actions выполняет `mvn -B clean verify`. Локальный интеграционный тест `MiniAppFlowTest` проверяет создание обращения, загрузку файла, явное создание issue, очередь и роль диспетчера, переход статуса, поиск дубля с учётом места и присоединение.

## Изменения относительно исходного ТЗ и первого каркаса

| Область | Текущее решение |
| --- | --- |
| Структура | Модули разделены на один запускаемый Java-сервис и девять библиотек/модулей ресурсов. Для библиотек отдельные `application.yaml` не нужны. |
| Webhook | HTTP-контроллер расположен в `api`, реализация Redis-очереди — в `app-bootstrap`; в ТЗ вход webhook описан в `integration-max`. |
| Контроллеры | Добавлены маршруты всей OpenAPI-спецификации, аннотации валидации и типизированные перечисления. `@Validated`-контроллеры оставлены не `final`, чтобы Spring мог создать CGLIB-прокси. Незавершённые операции возвращают `501`. |
| Версии | В сборке зафиксированы Flyway `9.16.3` и SQLite JDBC `3.43.0.0`; в ТЗ указаны Flyway `9.22.x` и SQLite `3.46`. Версии ТЗ и проекта нужно согласовать перед релизом. |
| Compose | Добавлены проверки готовности сервисов. Для локального MinIO используется community-образ Coollabs, закреплённый по digest: прежний образ не загружался. Выбор S3-хранилища для промышленной среды остаётся отдельным решением. |
| Конфигурация Flyway | Автоматическая очистка БД при ошибке миграции выключена (`clean-on-validation-error: false`, `clean-disabled: true`). |

История этапа: создан Maven-каркас и схема БД; затем уточнены версии зависимостей и Dockerfile; добавлены типизированные поля, валидация и покрытие маршрутов; исправлен запуск `@Validated`-контроллеров; заменён недоступный образ MinIO; выполнена проверка Compose; добавлены параметры очистки Flyway для разработки. Детали отдельных правок можно смотреть в истории коммитов ветки.

## Что проверено на практике

24 сентября 2026 года `docker compose -p pulse-doma-check up --build -d` собрал backend и поднял все четыре контейнера до состояния `healthy`. Spring Boot запустился, Flyway применил миграцию V1, `/actuator/health` вернул `UP`, endpoint здоровья MinIO ответил `200`. Проверочный webhook с верным секретом вернул `200` и увеличил длину Redis-очереди с 0 до 1; неверный секрет вернул `401`, некорректное тело — `400`. После проверки контейнеры и сеть остановлены через `docker compose -p pulse-doma-check down`; volumes с данными сохранены. Проверка проводилась до добавления двух параметров Flyway в последнем коммите тиммейта.

Maven-сборка и тесты также прошли в [GitHub Actions](https://github.com/rommerrro-gh/vega2124/actions/runs/36029444359). Этот запуск подтверждал сборку каркаса и перечисленные smoke-проверки на тот момент; он не проверял сценарий с реальным ботом MAX, загрузку вложений или критерии приёмки ТЗ.

27 сентября 2026 года локально прошёл `mvn verify` с миграцией V3 и тестами подтверждения, отказа, повторного открытия, истечения 72 часов и HTTP-запроса к локальному двойнику MAX API. В браузере профиля `demo` проверен путь от создания заявки до ответа жителя «проблема осталась». Отдельный Compose-стек поднял все четыре контейнера до `healthy`; backend ответил `UP`, а реальный `MinioAttachmentStore` записал и прочитал тестовый объект без изменения байтов. После проверки временные контейнеры и тома удалены. Отправка уведомления в настоящий MAX и запуск в его клиенте ещё не проверялись.

Для стендовой проверки подготовлены [порядок подключения MAX](max-staging.md), скрипт проверки HTTPS и токена, явные команды регистрации/удаления webhook и инструмент для создания тестового дома, приглашения и роли диспетчера. Они проверены локально с временной SQLite БД и локальным HTTP-двойником API.

27 сентября 2026 года получен токен тестового бота `t802_hakaton_max_bot`: официальный MAX API принял его при запросе `GET /me` с доверенным корневым сертификатом Минцифры. Токен хранится только в локальном `.env`, который исключён из Git; примерный секрет webhook заменён случайным. Повторно запущенный локальный Compose-стек ответил `UP` на `/actuator/health`. Попытка открыть стенд через временный Cloudflare Tunnel не завершилась: туннель не смог разрешить DNS-имена Cloudflare, а выданный HTTPS-адрес отвечал `530`. Публичный адрес для mini app пока не готов, webhook не зарегистрирован; запуск внутри клиента MAX и доставка уведомления не проверены.

28 сентября 2026 года обновлённый React-интерфейс проверен в локальном профиле `demo`: мини-приложение открылось без запроса пароля, загрузило два дома, прошло путь от формы через поиск похожих обращений до создания заявки. Новая заявка появилась в «Моих заявках» и очереди диспетчера; её карточка открылась в кабинете. Проверены настольная и мобильная компоновки. Это проверка локального интерфейса, не запуск внутри клиента MAX.

## Что ещё предстоит

1. Завершить приглашения и выбор активного дома для нескольких домов; доработать зону формы до структурированных подъезда, этажа и объекта вместо одной строки.
2. Проверить путь `mini app → report → candidates → join/create → кабинет диспетчера → уведомление → приёмка` в реальном клиенте MAX с рабочим ботом и токеном. Подготовка стенда и роли описаны в [инструкции](max-staging.md). Повысить надёжность Redis-очереди при аварии между LPOP и обработкой; отправка уведомлений имеет семантику «как минимум один раз» при аварии после ответа MAX до отметки в outbox.
3. Завершить бизнес-операции заявок, обращений, инцидентов, данных дома и интеграций; убрать `501` только после реализации и тестирования соответствующего сценария.
4. Добавить антивирусный hook, правила хранения и очистки вложений; проверить загрузку через HTTP API на отдельном окружении с настоящим MinIO и подписанной авторизацией MAX.
5. Согласовать версии зависимостей, затем проверить критерии приёмки и нефункциональные требования из ТЗ на отдельном окружении.

При каждой следующей правке указывайте здесь фактическое состояние, подтверждённые проверки и оставшиеся ограничения. Для содержательных изменений синхронно обновляйте OpenAPI и README.
