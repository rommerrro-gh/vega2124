# Пульс дома

Проект по техническому заданию версии 1.1 и продуктовой концепции версии 1.0. Реализован путь от формы mini app и выбора дубля до очереди диспетчера, подтверждения результата жителем и закрытия заявки. Передача во внешнюю систему пока не реализована.

Фактическое состояние, изменения относительно ТЗ, результаты проверок и оставшаяся работа описаны в [документе о текущей реализации](docs/current-implementation.md).

## Запускаемые сервисы и библиотеки

| Компонент | Роль |
| --- | --- |
| `app-bootstrap` | Единственный запускаемый Java-сервис; собирает исполняемый JAR и владеет `application.yaml`. |
| `api` | Библиотека HTTP-контроллеров и входных DTO. |
| `integration-max`, `integration-external` | Библиотеки адаптеров внешних систем. |
| `domain-identity`, `domain-issues`, `domain-duplicates`, `domain-house`, `common` | Библиотеки модели, правил и общих контрактов. |
| `infra` | Библиотека ресурсов: миграция SQLite, спецификация OpenAPI и демонстрационные данные. |

В `compose.yaml` также запускаются вспомогательные инфраструктурные сервисы Redis и MinIO, а `contract-adapter` — отдельная демонстрационная заглушка на nginx. Они не являются Maven-модулями. Для локальной разработки MinIO берётся из [community-сборки Coollabs](https://github.com/coollabsio/minio), закреплённой по digest: [MinIO Community теперь распространяется как исходный код](https://github.com/minio/minio#source-only-distribution), а прежний образ из Quay не загрузился при проверке Compose. Эта сборка предназначена только для локального окружения; для производственного развёртывания выбор и сопровождение S3-хранилища требуют отдельного решения. Параметры Java-сервиса, включая порт, адреса Redis, MinIO, MAX API и адаптера, задаются в `app-bootstrap/src/main/resources/application.yaml` и могут переопределяться переменными окружения. Библиотекам отдельные `application.yaml` не нужны: они не запускаются самостоятельно и получают настройки от `app-bootstrap`.

## Локальный запуск

Для сборки вне контейнера требуются Java 21 и Maven 3.9.x. Для запуска через Compose нужен Docker Compose; Dockerfile сам использует Java и Maven внутри контейнера. Создайте `.env` из `.env.example` и замените значения для локальной среды. Затем:

```sh
docker compose up --build
curl http://localhost:8080/actuator/health
curl -i -X POST http://localhost:8080/webhooks/max \
  -H 'Content-Type: application/json' \
  -H 'X-Max-Bot-Api-Secret: replace-with-random-local-secret' \
  -d '{"update_type":"bot_started","timestamp":0}'
```

Контейнер поднимает backend, Redis, MinIO и явно маркированный contract adapter. SQLite хранится в volume `sqlite-data`. Для реального webhook нужен внешний HTTPS endpoint на порту 443 с доверенным сертификатом и зарегистрированная подписка MAX; локальный порт 8080 предназначен для разработки.

Демонстрационный набор в `infra/seed/demo.sql` можно вручную применить после миграции к локальному файлу SQLite. Автоматически он не загружается.

### Mini app

Интерфейс жителя и кабинет диспетчера находятся в `frontend/`: React и компоненты MAX UI оформлены цветами «Пульса дома». Для изменения фронта установите Node.js и pnpm, затем выполните:

```sh
cd frontend
pnpm install --frozen-lockfile
pnpm build
```

Сборка создаёт `bundle.js` и `bundle.css` в `app-bootstrap/src/main/resources/static/miniapp/`. Эти файлы хранятся в Git, поэтому Docker и Maven запускают приложение без Node.js. После изменения фронта пересоберите контейнер: `docker compose up --build -d`. HTTP API и Java-сервис при переходе на React не менялись.

Для локальной демонстрации включите профиль `demo` через `SPRING_PROFILES_ACTIVE=demo` и откройте `http://localhost:8080/miniapp/index.html`. Профиль создаёт два дома, жителя, диспетчера и администратора первого дома. Кабинет диспетчера открыт по `http://localhost:8080/dispatcher/index.html`, кабинет администратора — по `http://localhost:8080/admin/index.html`. Для просмотра входа администратора из mini app используйте `http://localhost:8080/miniapp/index.html?demoSession=admin`. Только в профиле `demo` заголовки `X-Demo-Session: true`, `dispatcher` и `admin` открывают тестовые роли. В обычном профиле сервер проверяет подписанную строку `WebApp.initData` из заголовка `X-Max-Init-Data` по токену `MAX_BOT_TOKEN` и сроку в один час. Новый MAX-пользователь создаётся при первом корректном входе; дом добавляется по приглашению `?invite=<token>` или через `start_param` MAX. Токен приглашения хранится в БД только как SHA-256 hash.

Форма принимает категорию, место, время и описание, до пяти файлов JPEG/PNG/PDF/MP4 по 10 МБ. В профиле `demo` файлы сохраняются в `./data/demo-attachments`, в обычном профиле — в частный bucket MinIO `pulse-doma-attachments`. Доступ к файлу есть у автора обращения, участников связанной заявки и диспетчера дома. Файлы хранятся без анализа содержимого; антивирусная проверка и политика удаления ещё не добавлены.

Стартовый экран жителя показывает один общий выбор дома, кнопку «Сообщить о проблеме» и короткие сводки по заявкам, опросам и паспорту дома. Разделы раскрываются по нажатию; сведения и заявки относятся к выбранному дому. Если заявка ожидает подтверждения выполненных работ, над основным действием появляется напоминание.

Раздел «Паспорт дома» показывает адрес и заполненные поля с источником и датой получения. Доступ есть только у пользователя с подтверждённым членством в этом доме. Если поля ещё не внесены, интерфейс показывает пустое состояние. В профиле `demo` у первого дома есть явно помеченные демонстрационные значения; автоматическое получение сведений из ФИАС и ГИС ЖКХ пока не подключено.

Подтверждённый `HOUSE_ADMIN` может в своём доме добавлять, изменять и удалять публичные локальные и аварийные контакты, а также создавать приглашения жителям со сроком 1–30 дней и лимитом 1–100 активаций, просматривать их состояние и отзывать. Контакты появляются в паспорте с датой обновления; операции пишутся в аудит. Токен нового приглашения показывается только один раз, в списке и аудите его нет. Роль администратора нельзя получить обычным приглашением: для тестового стенда её выдаёт доверенная команда `scripts/max_staging_seed.py admin` после первого входа пользователя в MAX. Администратор не меняет официальные поля ФИАС/ГИС ЖКХ и не получает права диспетчера.

Администратор может создать для своего дома предварительный опрос с двумя или более вариантами и датой закрытия. Подтверждённый житель видит опрос в mini app и может проголосовать один раз. Итоги показываются сразу или после закрытия — по выбору администратора; имена проголосовавших не раскрываются. Такие опросы не являются официальным голосованием собственников.

Раздел «Мои заявки» позволяет открыть заявку повторно. Когда диспетчер отмечает работу выполненной, участники получают 72 часа на ответ в мини-приложении. Все подтверждения закрывают заявку; сообщение о нерешённой проблеме возвращает её в очередь диспетчера. Если ответов не хватает к концу срока, заявка закрывается без подтверждения. Участникам с привязанным MAX ID бот отправляет сообщение через очередь исходящих уведомлений. Для отправки нужен `MAX_BOT_TOKEN`; в профиле `demo` сообщения наружу не отправляются.

Диспетчер может установить плановую календарную дату исполнения заявки и перенести её с обязательной причиной. Житель видит текущую дату и историю переносов; просроченный текущий срок выделен красным. Даты считаются по московскому времени. Изменения также ставятся в очередь уведомлений MAX. В предварительных опросах видимые итоги показывают проценты и число голосов, а администратор добавляет варианты ответа отдельными полями.

Житель может отозвать своё обращение до начала проверки выполненных работ. Обращение и его связь с заявкой остаются в истории с отметками отзыва и отсоединения; если это было последнее обращение, новая заявка закрывается, а взятая в работу попадает диспетчеру на разбор. Диспетчер может объединить активные заявки одного дома, выбрав основную заявку той же или более поздней стадии, и выделить одно из нескольких обращений в новую заявку. Для этих действий действуют проверки роли и запись в аудит.

Открытие страницы в обычном браузере без профиля `demo` не даёт доступ к API. Для реального запуска нужен опубликованный HTTPS адрес mini app, настроенный бот MAX, его токен и действующее приглашение в дом.

Порядок подключения тестового бота, публичного стенда и двух тестовых ролей описан в [проверке в настоящем MAX](docs/max-staging.md). Скрипт `scripts/max_staging.py check` проверяет готовность стенда без вывода секретов; регистрация webhook выполняется отдельной командой `subscribe`.

## Состояние реализации

- Работают схема SQLite, FTS5 для заявок и триггеры, webhook с постановкой JSON в Redis и worker для `message_created` с повторными попытками и Redis Set по `body.mid`.
- `ReportService` сохраняет обращение и ищет кандидатов того же дома, категории и места; он не создаёт заявку до выбора жителя. Mini app вызывает отдельные операции создания или присоединения. Автор берётся из проверенных данных MAX, а сервер проверяет членство в доме и принадлежность обращения.
- Все маршруты из `infra/openapi.yaml` имеют контроллеры. Незавершённые операции возвращают 501. Доступ к `/v1/**` требует подписи MAX; профиль `demo` изолирован от обычного запуска.
- Кабинет диспетчера показывает очередь только разрешённого дома и позволяет пройти переходы `DRAFT → OPEN → ASSIGNED → IN_PROGRESS → RESOLVED` с причиной, записью в историю и аудит. После `RESOLVED` начинается `VERIFICATION_72H`; отказ жителя переводит заявку в `REOPENED` для повторной работы.
- FIAS/GIS/UK contract adapter — демонстрационная граница, он не выдает модельные ответы за официальные данные.
- `RequirementsTrace.java` перечисляет все FR, AC и NFR; наличие ID в коде не означает выполнения требования.

## Важные решения

SQLite открывается с WAL, `busy_timeout=5000`, `foreign_keys=ON`; размер пула Hikari — 1. Кандидаты дублей выбираются в пределах `house_id` за 30 дней при совпадении категории и нормализованного места. Рейтинг учитывает категорию, место, давность и текст. Исходный `report` хранится отдельно от общей `issue`.
